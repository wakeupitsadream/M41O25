## Что считаем «стабильно»

1. Production собирается из `main` автоматически при каждом push, перед ним CI; есть откат на предыдущий деплой.
2. Ежедневный бэкап уходит в R2, восстановление отрепетировано один раз на реальном дампе.
3. Чек-лист на физическом iPhone пройден: установка, вход в установленном приложении, ночь → утро, авиарежим, шторка с клавиатурой, фото и PDF, шаринг дня.
4. Распознавание проверено на трёх реальных сканах с измеренной точностью; ручной ввод остаётся запасным путём.
5. Ошибки и cron видны: карточка диагностики в админке, внешний «сторож» по cron, runbook на случай падения.
6. Гигиена доступа: инвайт-код не угадывается и не лежит в логах, `SEED_*` удалены, второй админ, смена PIN, ввод кода терпим к кириллице.
7. Регрессии ловятся: typecheck, lint, проверка миграций, unit и e2e в GitHub Actions; CLAUDE.md с правилами проекта.
8. Решены публичность репозитория и заметка о персональных данных.

## Открытая проблема P0: зависание клиентской навигации в production-сборке

Симптом. В production-сборке (`next build` + `next start`, Chromium/Playwright с эмуляцией iPhone 15) переход по ссылке, `router.push/replace` после server action или `router.refresh()` иногда не завершается: URL не меняется, ошибок в консоли и на сервере нет, RSC-ответ приходит целиком, главный поток отвечает. Повторный тап не помогает (добавляет ещё один зависший transition), помогает только перезагрузка страницы. На dev-сервере не воспроизводится ни разу.

Воспроизведение. Наполнить страницу назначения (например, 100 контактов или 100 новостей в локальной базе), собрать production-сборку и запустить `e2e/nav-hang.mjs` (в `npm run e2e` не входит; переменные `TARGET`, `FROM`, `TRIES`, `MODE=buffer`, `SW=1`). Вероятность растёт с объёмом страницы назначения: контакты из 105 строк — 6/6 и 8/8, новости из 118 — около 75 %, лента и рулетка — 1/4, задачи — около 1/3, контакты из 15 строк — 1/6. Домашка из 106 карточек, опросы, дни рождения, вопросы, `/me` и `/admin` — 0 из 4. Тот же механизм ломает `router.refresh()` после server action: галочка в задаче остаётся `disabled` (так падал `e2e/group.mjs` и локально, и на GitHub Actions на свежей демо-базе, то есть на маленькой странице — вероятность зависит не только от объёма).

Что исключено. Service worker (сборка с `disable: true` виснет так же), prefetch ссылок, `motion` и `useOptimistic`, многобайтовые символы в данных, количество `Link` на странице, `RefreshOnResume`/`NetStatus` в лэйауте. Воспроизводится на сборке 36f18cf, то есть проблема существовала до правок этапов 1–4.

Что установлено. Если отдавать браузеру RSC-ответ одним куском (`MODE=buffer`), зависаний 0/6 против 6/6 — виновата гонка на границах чанков потока, а не данные. Сам поток страница вычитывает целиком (65–78 чанков, 196 КБ за 45 мс, `done=true`), так что транспорт, сжатие и service worker ни при чём. Состояние React после зависания: `pendingLanes = suspendedLanes = warmLanes` (transition-лейны), `pingedLanes = 0`, `callbackNode = null` — React ждёт «ping» от thenable, а thenable уже резолвился, ping потерян. Thenable — ленивые чанки Flight: сервер выносит элементы в отдельные строки, как только текущая строка превышает 3200 байт (`react-server-dom-webpack`, `deferTask`), поэтому любая страница крупнее нескольких килобайт приходит десятками ленивых строк, которые резолвятся прямо во время рендера перехода. Это ошибка React внутри Next 15.5.25 (там вшит `19.2.0-canary-0bdb9206-20250818`, август 2025); в dev-сборке другие тайминги. Актуальный Next 16.3 несёт более новый React — проверка на нём идёт отдельным экспериментом.

Обход в приложении. `components/features/nav-guard.tsx`: `NavWatchdog` в трёх лэйаутах слушает клики по внутренним ссылкам и отправки форм, `useGuardedRouter` заменяет `useRouter` в клиентских компонентах. Если ответ на fetch страницы (по `performance.getEntriesByType("resource")`) пришёл, а через 2,5 с ни URL, ни дерево (счётчик коммитов лэйаута), ни кнопка формы не изменились — уходим обычной навигацией браузера: на адрес ссылки, на адрес из ответа server action (заголовок `x-action-redirect`) или перезагрузкой страницы. Ложных срабатываний при медленном сервере нет: пока ответ не пришёл, сторож ждёт (до 30 с). Это костыль: переход занимает на 2,5 с дольше и идёт с полной перезагрузкой, зато тап никогда не «умирает».

Эксперимент с Next 16 (05.09, отдельный worktree, ветка `worktree-wf_93be95ca-115-1`, коммит f37eea0). Next 16.3.4 с React 19.2.8 без сторожа: 0/8 зависаний на контактах из 103 строк, 0/8 на новостях из 109, 0/12 с включённым service worker — против 6/6 и 8/8 на Next 15.5.25. Что потребовалось: `next build --webpack` (Serwist), `middleware.ts` → `proxy.ts` с экспортом `proxy`, прямые импорты `eslint-config-next/core-web-vitals` и `eslint-config-next/typescript` вместо FlatCompat, версии пакетов, `next dev` без флага turbopack; next.config.ts и @serwist/next 9.5 менять не пришлось. Цена: 11 ошибок новых правил react-hooks (React Compiler: set-state-in-effect в app/error.tsx, forms.tsx, scan-recognizer.tsx, enter-install-hint.tsx, install-hint.tsx, birthday-banner.tsx, use-schedule.ts; refs в schedule-app.tsx; immutability в use-schedule.ts; purity в app/admin/page.tsx) — их надо починить или понизить до предупреждений.
